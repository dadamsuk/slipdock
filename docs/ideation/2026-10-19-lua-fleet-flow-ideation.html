Grounding Context

What the screenshot shows. A board with tabs for Board, Velocity, Attention (with a badge), In work and Fleet health. The header has a "Fleet healthy · updated just now" pill and a pause button. Filters: All / Agent / Human, plus "Stuck only" and "Needs owner". A stats strip shows: in flight 61 (57 agent · 4 human), waiting on a human 4 (oldest 41m), done in 7 days 1,288, cycle time P50 47m / P85 3h, and moves in 24h 926 (898 forward · 6 back). Column headers carry WIP limits (10/20) and in/out counts. The 311-card backlog is collapsed to a tile ("oldest 2d · Show cards"). There is a dedicated "Waiting on human" column. Each card shows its ID, priority, a robot or person icon, time in its current stage, a status chip, a PR number and a reason line such as "waiting on a reviewer". A "Fleet stages / Linear states" toggle suggests Lua sits on top of Linear.

Codebase Context (checked against the repo).

  • No movement history. A move is logged only as free text, moved “title” to <list>. The source list and the actor are not recorded (lib/slipdock/boards.ex:2175, lib/slipdock/boards/activity.ex). No card has a column-entered time. The only time-based numbers are sprint burndown and velocity (lib/slipdock/sprints.ex). The narrative view and the completed_at backfill both parse message wording.
  • Waiting on a person is a bare flag. @flags ~w(flagged blocked review waiting starred) (lib/slipdock/boards/card.ex:6) records no set time, no reason and nobody it waits on. The unattended job prompt says: "comment, flag the card waiting and stop". The code comment beside it reads: "an agent that stops to ask waits for ever" (lib/slipdock/automations/runner.ex:287-290).
  • Nothing gathers what needs a person. My work is grouped only by due date (lib/slipdock/work.ex). Alerts appear in the header bell ("Nothing needs your attention."). There is no per-person queue. After repeated requeues, recovery flags a card blocked without telling anyone.
  • Fleet control. The only off-switch is enabled on each rule; runners, pools and boards cannot be paused. Runner status reads "job N", "seen X ago" or "never seen". WIP limits are display-only, because move_card never checks them. wait_while_doing is the one form of back-pressure that already exists.
  • Card face. A runner job's state shows only in the card modal (card_sections.ex:490-501), never on the tile. There is no time-in-list display, no human-readable card code and no PR handling. Card colour is a strip along the top.
  • Scale. Each column loads all of its cards, with no cap. Swimlane collapse is held in memory and lost on reload (show.ex:168). A lane header shows only a count. Column categories (todo/doing/done/dropped) already exist and drive completion.
  • Product boundary. Slipdock must stay generic. Agent features should sit on the same card model and be invisible on boards without agents. CLAUDE.md expects each feature to reach the CLI, the agents page, the skills and the README, with tests.

External context. No product or repo called "Lua" or "fleet-flow" turned up in a search, so the screenshot is the only evidence. Agent boards (Vibe Kanban, Cline Kanban, KanBots, GitHub Agent HQ, Linear agents) are converging on board + worktree + PR + a human review gate. What sets them apart is moving to supervision: what needs a human and what is stuck. Vendor dashboards report adoption (code generated) rather than flow. Flow-metrics practice uses P50/P85 cycle time and treats a card as aging once it passes the P85.

1. Ask a human, and the answer restarts the work

I1Waiting on a humanConfidence 75%Complexity High
Description
Replace "flag it waiting and stop" with an actual question. An agent (or a person) opens a wait on a card. The wait records what is needed, who it is waiting on (a named person or "anyone"), when it was opened, and optionally a short list of answer choices. The tile shows "waiting on Dana · 41m" as its reason line. Someone answers from the card, from My work, from the CLI or by email. The answer is posted as a comment, closes the wait, and re-queues a job for the same runner pool with the answer and the handoff at the top of the prompt. The waiting flag stays as the filter everyone already uses, but it is now derived from whether a wait is open. An optional later step: if nobody answers within a board-set response time, the wait raises an alert, and accepting the wait stops the clock (the andon idea).
Basis
direct: automations/runner.ex:287 "an agent that stops to ask waits for ever" and :290 "comment, flag the card waiting and stop". direct: card.ex:6 flags have no set time and no owner. api_guide.ex:1025-1027 has two human-wait flags, waiting and review, and neither names who is being waited on. direct: snooze.ex:103 wake_on_activity already wakes a card when someone else comments, so the trigger exists. external: the call-centre "virtual hold" callback, where the caller is called back instead of holding on the line.
Rationale
Lua counts "waiting on a human: 4, oldest 41m", and its count ends there. Slipdock's own job prompt guarantees that an unattended agent hits a dead end whenever it needs anything. Closing the loop turns that dead end into a pause, and it is the strongest thing on this list that Lua's screenshot doesn't show. It is generic too: "waiting on the supplier for a quote" on an ops board uses the same record and has no agent in it at all.
Downsides
This is a new record, a new job state or re-queue path, and changes to the API, MCP, CLI and skills. The resume needs care with leases and with the existing requeue_stuck cap. The escalation clock is extra weight and should wait until the loop has proved itself.

2. A movement ledger, and a board pulse built on it

I2Flow numbersConfidence 85%Complexity Medium
Description
Record every move between lists as a structured row: card, from list, to list, both categories, who moved it (person, agent token or automation) and when. Backfill it once from the existing activity text. On top of the ledger, add one pulse query: in progress, waiting, done this week, typical time to finish (P50/P85), moves in the last 24 hours forward and back, and per-list in/out counts. Serve the pulse first as a CLI command and an MCP tool. Then render it as an opt-in strip that reads in plain words on any board, for example "6 on the go · 2 waiting on Dad since Tuesday · 23 done this week · usually takes a day".
Basis
direct: boards.ex:2175 logs moved “title” to <name> without the source list, even though do_move_card already holds from_column. Automations receive from/to in card_moved events, but nothing persists them. direct: a grep for moved_at|entered_at|column_entered in lib/ and migrations finds nothing. direct: narrative.ex:270-278 and the completed_at backfill both depend on message wording. direct: docs/roadmapping-features.md:165 already lists "Time in column / cycle time" as a small item. external: P50/P85 cycle time is the standard service-level measure.
Rationale
Every number in Lua's stats strip, its column in/out counts, "6 back" and the per-card stage times all depend on this one missing record. It is the foundation for ideas 4 and 7. Adding actor kind is the cheap way to get "57 agent · 4 human" without inventing an agent user type. Shipping the pulse to the API first means agents can act on it, for example by not starting new work while the waiting pile is deep. Lua's strip is display only.
Downsides
A new table that grows quickly on agent-speed boards, so it needs indexing and possibly retention. The backfill from text is best-effort. Percentiles on small boards are noisy and need a minimum sample before they are shown.

3. "Waiting on me" in My work

I3Waiting on a humanConfidence 75%Complexity Low–Medium
Description
This is Lua's Attention tab, built into the surface Slipdock already has rather than as a new dashboard. Add a top section to My work, "Waiting on you", with a count in the header. Cards appear there oldest first, with the reason, when one of these is true: someone flagged them review or waiting and they are assigned to you; recovery parked them as blocked; a runner job failed on them; or they sit in a doing list with nobody on them, which is Lua's "Needs owner". Add the same section to slipdock work and to the plan-my-day MCP prompt, so an agent can say "three things are waiting on you". Once idea 1 exists, open waits addressed to you feed this section directly.
Basis
direct: work.ex sections are overdue / today / week / later / none / done, with no grouping for waiting or review. direct: the only attention surface is the alert bell ("Nothing needs your attention", layouts.ex:1166). direct: recovery.ex:151-156 flags a card blocked and "left where it is", with nobody notified. direct: layouts.ex:1524-1533 "a queue with no badge is a queue discovered a month late."
Rationale
The signals already exist but are scattered across flags, recovery, alerts and assignees. A section built from those signals adds no new data and works on every board, because "things waiting on you" means the same thing on a chores board as on a coding board. The verifier pushed this down from a separate inbox to a My work section, which is cheaper and avoids a second home page.
Downsides
"Needs owner" needs a rule for which lists count as doing, which the categories supply. Unless it is filtered, review flags on other people's cards could add noise.

4. Stuck means past this list's usual

I4The card faceConfidence 70%Complexity Medium
Description
When a card enters a list, compute the usual stay from the 85th percentile of that list's own history, taken from the idea 2 ledger. The tile carries a single age chip: "In Review 3h" in neutral colours, turning amber once the card has stayed longer than usual ("1h over usual"). That gives Lua's "Stuck only" toggle a definition that needs no tuning, as a filter and a search operator. The chip picks the clock that suits the card: time in list for fast lists, days since the last update for slow ones, and slip past the due date for dated cards. Below a minimum amount of history it falls back to a number set per list, or shows plain age.
Basis
direct: the gardener calls a card stale after a fixed 14 days (stale_in_progress.ex:2-14), and the automation preset uses 7 days (automations.ex:68). Both are blind to a three-minute agent card that has been hanging for two hours. direct: api_guide.ex:1010-1012 "A card sitting in doing for hours ... looks abandoned" is a convention, not data. external: aging WIP measured against P85, and hospital "expected discharge" boards.
Rationale
Time-in-stage is the most useful thing on Lua's card face. A threshold that adjusts itself is the only one that works on both a quarterly roadmap board and a fleet of agents. It also replaces two hard-coded staleness rules with one measure.
Downsides
It depends on idea 2. Percentiles on boards with little history can mislead, and an amber chip that fires too often becomes noise.

5. Pause, with a reason, and say why work is held

I5Agent fleet controlConfidence 70%Complexity Low–Medium
Description
One brake, scoped to a board or a runner pool, with a required reason: "bad deploy, hold everything". While paused, nobody can claim a job or send the top card. Jobs already running finish, and the drain on shutdown already handles this. A banner names who paused it and why. A held job or card gets a single "held because" line: "paused by David: bad deploy", "Review is full (10/10)" or "no runner online for pool dev". The second of those makes WIP limits act as opt-in back-pressure on automated claims, while people moving cards still only see the warning badge. A circuit breaker that pauses the pool after N failures in a row is a later option.
Basis
direct: a grep for pause across the runner and automation code finds no field; the only off-switch is a per-rule enabled (runners.ex:141-146). direct: move_card never checks wip_limit (boards.ex:2169); the badge alone shows it (board_view.ex:497-509). direct: job.ex:35 wait_while_doing is back-pressure that already exists, tied to "anything in doing". direct: claim_drain.ex already answers "nothing queued" while a deploy is draining. external: the Toyota andon cord, and a restaurant expo station that stops firing tickets once the pass is full.
Rationale
Lua's pause button is the one control someone supervising a fleet reaches for in an incident. In Slipdock today, stopping a runaway means disabling rules one at a time. The "held because" line shows any reader, including an agent reading list_cards, that the board stopped its work on purpose, which is better than a silent queue.
Downsides
Users need to understand how a pause scope (pool, board) interacts with the existing rule switches. WIP gating is contested for people, so keep it to automated claims and make it opt-in. The fleet health pill is useful only on boards that have runners, so hide it everywhere else.

6. Show the runner job on the tile, through one state line

I6The card faceConfidence 75%Complexity Low
Description
Write one function that derives a card's current state line from its open job, wait, flags, handoff and assignee, for example "Running · runner-2 · 7m", "Queued · no runner online", "Failed 3× · needs owner" or "Waiting on reviewer · 41m". Render it on the tile, with a small robot or person mark when a job holds the card. Return the same line in list_cards, the CLI and MCP output. The All / Agent / Human filter comes from the same derivation, so cards on boards without agents never show it.
Basis
direct: runner jobs appear only in the card modal (card_sections.ex:490-501); the tile code in slipdock_components.ex has no job reference. direct: the agent's name is already on its API token (accounts.ex:944-946 "whose label names the agent holding it"), and on the job as runner_name. direct: the footer badge order (slipdock_components.ex:1072-1085) leaves a natural slot.
Rationale
The question a supervisor asks most is "is anyone actually on this?", and today the only way to answer it is to open each card. Because one function feeds every surface, each later signal (idea 1's waits, idea 4's age, idea 5's holds) shows up on the tile, the CLI and MCP without extra work for each.
Downsides
It needs a density decision, since the compact tile is already crowded. The verifier rejected the larger "one holder per card" framing, because a card can legitimately have both a job and an assignee. This version only shows state; it doesn't enforce a lock.

7. Summary tiles for big and quiet lists

I7Board shape at scaleConfidence 70%Complexity Medium
Description
A list in the todo or done category, or any list over a size threshold, can collapse to a single summary tile: count, oldest card, a small age bar and "Show cards". Done can read as a counter ("+23 this week") rather than a pile. Swimlane headers get the same one-line summary ("6 in progress · 23 done this week · oldest 4d") instead of a bare count. Collapse state is saved in the saved view, which the URL already addresses, instead of resetting on reload. A collapsed list doesn't load its cards, which also caps board load.
Basis
direct: show.ex:168 swim_collapsed: MapSet.new() keeps collapse in memory only. direct: lane headers show a count badge only (swimlane_components.ex:1202-1203). direct: column.ex:34 preloads every card in the column with no limit. direct: categories exist (column.ex:8), which decides which lists collapse by default. direct: state.ex:95-97 "The URL is the source of truth: ?view=ID loads a saved view".
Rationale
Lua's "311 · oldest 2d" tile is the screenshot's answer to scale. A board that agents fill quickly becomes unusable to scan, and slow to load, without something like it. The same tile serves a human team's 300-card backlog.
Downsides
The age and in/out parts of the summary are much richer once idea 2 exists; without it, the tile can show only count and oldest by creation date. Drag-and-drop into a collapsed list needs a design.
