# Setting up an agent

Slipdock is built to be worked by an agent as well as by a person: Claude,
ChatGPT, Codex, a cron job you wrote yourself — anything that can make an HTTP
request. This page is how you get one connected. It takes about a minute, and
installing software is optional.

The one thing to be clear about before you start, because it is what confuses
everybody: **the agent does not run on the server.** It runs wherever you
already use it — your laptop, a cloud session, your editor — and talks to
Slipdock over the web, exactly as your browser does. You do not need shell
access to the machine Slipdock is running on. If you are using the hosted
version at [app.slipdock.us](https://app.slipdock.us) you have no such access
and do not need any; if you self-host, the shell on that box has nothing to do
with this.

So an agent needs three things, and only the first two are required:

1. **The address of your Slipdock.**
2. **Your approval, once** — which gets it a token that acts as you. Required
   before it can see anything of yours at all, not just before it writes.
3. Optionally, **the skills**: longer instructions, installed where your agent
   looks for them.

In the app, **Set up an agent** (in the avatar menu, or under Account) has all
of this with your own server's address already filled in, ready to copy.
**Help → Agents** (`/help/agents`, open to anyone, signed in or not) is the short version for
somebody choosing: each way in — the guide and API, MCP, the CLI, the skills,
runners and webhooks — with when to use it, a table of what each supports, and
a page per way in. The CLI's page links to a command reference
(`/help/agents/cli/reference`): every command in `slipdock help`, by group, with
a filter.

## 1 · Point it at the board

Paste this at the start of a session, with your own address in it:

```
Work from my Slipdock board at https://app.slipdock.us. Read
https://app.slipdock.us/api/guide?section=short and follow it, fetching a
section it names when the task needs one. Nothing about my boards is
readable until you sign in, so start with the device flow the guide describes
and tell me the code to approve.
```

That is the whole of the minimum setup. `GET /api/guide` is the one thing on
the server that needs no token, and it is written for agents rather than for
people: the model (top-level cards are epics, their subcards are the work),
what a card means on these boards, how to choose what to do next, what to write
back as it goes, and a `curl` line for every call it can make.

`?section=short` is the part an agent needs to work a board, ending with the
names of the other sections, and `?section=<name>` is one of them: `wiki`
before writing a page, `runners` before touching jobs, `automations` before a
rule, `recipes` for a call it can't place. `slipdock guide` and
`slipdock guide <name>` print the same, and over MCP `get_guide` gives the
short guide and `section` one of the rest. The whole guide (`?section=all`, or
the plain URL) is long, tens of thousands of words: a large share of a context
before the agent has read a card, so the skills and the prompt above never
start with it.

The guide is generated by the running server, so it is never out of date with
the API that answers. This is why the prompt points at a URL instead of
describing the API: a copied description rots, a URL does not.

## 2 · Approve it, once

This step is not optional, and it is not only about writing. The guide and the
skills are the only things on the server that are open; **everything about your
boards needs a token** — listing them, reading a card, searching, as much as
changing anything. Nobody but you can see your boards, and an agent is nobody
until you have said so. So expect it to ask almost immediately.

It asks with a device flow (RFC 8628, the same dance as a TV app):

1. The agent asks the server for a code.
2. It shows you a short code and a URL (`/activate`).
3. You open that in a browser you are already signed into, check the label it
   gives itself, and approve.
4. The agent is handed an API token a second or two later, and saves it in
   `~/.config/slipdock/token`.

Your password never goes near the agent, and a code is good for a few minutes
only. `slipdock auth` does the whole thing; an agent with only `curl` does it
in two calls, which the guide spells out.

Re-reading the guide **with** the token is worth it, and a good agent does it
unprompted: it then ends with your actual boards, every list on them, and which
list means ready, in progress and done — so it stops guessing at names.

**If you would rather hand over a token yourself**, make one under
**Account → API tokens** and give the agent that. It is also where you choose
how much rope it gets:

- **Read only** — it can summarise, search and report, and cannot change
  anything. A good default for an agent you are still learning to trust.
- **Read and write** — the normal choice for one that works the board.
- **Administer this server** — admins only, and nothing an agent needs unless
  it is managing users.

Every token is listed there with when it was last used and from where, and
**Revoke** ends its access at once. A token acts as you: it can see and change
exactly what you can see and change, and nothing else.

## 3 · Install the skills (optional)

The guide is enough on its own, and like the guide these need no token — they
describe the API rather than reveal anything on it. The skills are the
longer-form instructions,
and they help most with the parts that are about judgement rather than syntax —
what belongs on the wiki versus in a comment, how to work a backlog unattended,
how to leave a record someone will want to read. They are versioned with the
server that serves them, so a copy on your machine can be checked against the
API that actually answers.

On any machine with `curl` and `tar`:

```sh
curl -fsSL https://app.slipdock.us/install.sh | sh
```

That writes two things and nothing else:

- the skills into `~/.claude/skills` (pass a directory to put them elsewhere:
  `… | sh -s ~/somewhere`), and
- your server's address into `~/.config/slipdock/url`, so neither you nor the
  agent has to repeat it.

It signs nothing in. If you would rather read a script before running it,
`curl https://app.slipdock.us/install.sh` prints it; the skills are also
available as [a tarball](https://app.slipdock.us/api/skills.tar.gz) and as
[a JSON listing](https://app.slipdock.us/api/skills) of every file with a sha.

**One source for each skill.** A skill's text lives in one place: the server
that serves it (in Slipdock's repository, `priv/skills/`). The copy on your
machine is installed from there, never edited by hand: to change a skill,
change it in `priv/skills/`, and once that is deployed run the one-liner
again. A runner does that by itself: with *Keep the runner current* on (the
default for new installs) it puts the server's skills in its skills
directory before every job but a merge (`SKILLS_UPDATE=0` /
`$SkillsUpdate = $false` in its config keeps the script current but the
skills as they are; `SKILLS_UPDATE=1` / `$SkillsUpdate = $true` turns it on
alone). A skill folder that is a symlink is left alone. Slipdock's own
tests read only `priv/skills/`, never `~/.claude/skills`.

What you get:

| Skill | For |
| --- | --- |
| `slipdock` | The command and API reference: what each call does and when to reach for it. |
| `slipdock-work` | Working *from* a board: epics and subcards, what to pick up next, what to write back. |
| `slipdock-wiki` | The wiki: finding, reading, writing, linking, section writes. |
| `slipdock-docs` | The harder half of the wiki — what is worth writing down, and where it goes. |
| `slipdock-plan` | Planning: an idea becomes a plan the way the board's handbook Playbook says — sized as a card, a feature or a system, then the stages that size takes, written into the handbook and onto cards. |
| `slipdock-loop` | Working the ready list unattended, one card per pass, for `/loop` or a cron — watching the GitHub build after each push and never closing a card on a red one. |

### In ChatGPT

ChatGPT can't run the `slipdock` command, so it gets its own versions of the
skills, one zip each, from *Set up an agent* on the account page (or
`https://app.slipdock.us/api/skills/<name>/chatgpt.zip`, or all of them with
`slipdock skills chatgpt`). Each says which tool of the Slipdock connector to
use for each command, so connect ChatGPT to `https://app.slipdock.us/mcp` first
(see [Over MCP](#over-mcp)), then upload the zips as skills. `slipdock-loop` has no ChatGPT
version: it commits, pushes and watches builds, which a chat can't.

Board-specific detail — board codes, list names, tag vocabularies — is
deliberately **not** in these files. It comes from the guide (`slipdock guide`,
`/api/guide?section=short`), per caller. A
skill that hardcodes your board layout is wrong the first time you rename a
list; one that sends the agent to the guide first never is.

## 4 · The CLI (optional)

[The `slipdock` CLI](manual/cli.md) wraps every call, and is pleasanter to read
in a transcript than a wall of `curl`. It is an Elixir escript, so it needs
Erlang/OTP on the machine that runs it — which is why nothing above depends on
it. On Windows, one line in PowerShell installs it from the server, for you
alone, with Erlang through winget if there is none, and puts it on your PATH:

```powershell
irm https://app.slipdock.us/cli/install.ps1 | iex   # again later to update it
slipdock auth
```

Elsewhere, if you have Elixir:

```sh
cd cli && mix escript.build && cp slipdock ~/.local/bin/
slipdock url https://app.slipdock.us   # saved in ~/.config/slipdock/url
slipdock auth                          # the device flow; prints a code to approve
slipdock whoami
```

`slipdock url` with no argument says which server it is pointing at and where
that came from — the first thing to check when something cannot be reached.
`$SLIPDOCK_URL` and `$SLIPDOCK_TOKEN` still override the saved files, for a
one-off against another install.

## Agents that cannot run commands

The three paths above all assume the agent can make an HTTP request — true of
Claude Code, Codex, Cursor, a shell script, a cron job. A chat assistant with
nothing but web browsing can *read* a board you have shared publicly, but it
cannot sign in or write. If that is all you have, the thing to reach for is not
a different setup but a different tool: any coding agent will do, and the board
does not care which. If it speaks MCP, see [Over MCP](#over-mcp).

## Over MCP

This server is also an MCP server, at `https://your-server/mcp` (the
**Set up an agent** page shows this install's own address). It speaks
stateless Streamable HTTP, revisions 2025-03-26 to 2025-11-25. A client
that connects gets a small set of tools rather than the whole API:

| Reading | Writing |
|---|---|
| `whoami`, `get_guide`, `list_boards`, `get_board`, `list_cards`, `get_card`, `search`, `ask`, `read_page`, `list_pages`, `page_info`, `page_history`, `wiki_info`, `activity`, `download_file`, `list_automations`, `list_tools`, `garden`, `page_tool`, `job_log` | `create_card`, `update_card`, `move_card`, `comment`, `leave_handoff`, `garden_decide`, `upload_file`, `delete_attachment`, `complete_card`, `verify_card`, `status_update`, `archive_card`, `delete_card`, `create_list`, `create_tag`, `delete_list`, `create_board`, `update_board`, `archive_board`, `delete_board`, `write_page`, `quick_note`, `update_page`, `file_folder`, `share`, `revert_page`, `manage_wiki`, `card_views`, `manage_automation`, `install_tool`, `skill_registry`, `claim_job`, `job_progress`, `finish_job`, `keep_job_log` |

Files move without passing through the model: with a shell, `upload_file`
with `card` (or `page`) and `link: true` answers with a single-use
`upload_url`, good for ten minutes and needing no token, and
`curl -F file=@cv.docx -F sha256=<hex> <upload_url>` attaches the file as
`POST /api/cards/:id/attachments` would. `download_file` with `link: true`
gives a `download_url` the same way. So a scheduled task or a shared skill
needs no long-lived API token to move files
([details](manual/mcp-server.md)).

Whatever the door, a card's `handoff` is where it was left: `get_card` puts it
first, and an agent reads it before starting and leaves one (`leave_handoff`,
`slipdock handoff <id> --next "…"`) whenever it stops short. See
[the manual](manual/where-it-was-left-handoffs.md).

When an agent needs something only a person can give, it **opens a wait**
and stops, rather than flagging the card and hoping: `update_card` with
`wait` (`{"needs": "…", "question": "product", "choices": […]}`), `POST
/api/cards/:id/wait` or `slipdock wait <id> "…" [--kind K] [--on EMAIL] [--choice X]`.
The wait flags the card `waiting` and asks on it; somebody answers on the
card, in My work's **Waiting on you**, with `slipdock answer <id>` or
`answer_wait`, and the answer is a comment on the card. Several questions go
as `questions` (`--question Q --question Q`), never one block in `needs`:
each gets its own numbered answer box, and the answers come back one per
question (`answers`). A person may also **skip** them (`skip: true`,
`slipdock answer <id> --skip`): the card moves on unanswered and you use
your own judgement. `slipdock waits <id>` (`get_card` `waits: true`) shows
every question the card asked and the answers. **Give a wait its kind**:
`question` (`--kind K`), one of `product`, `ux`, `security`, `release` or
`other` (the default). A board routes each kind to the person whose call it
is (`wait_routes`: the first is who the wait is on, the rest are told), else
the wait goes to the board's owner; leave `on` out so the route can pick. The
owner sets the table on the board's Agentic Building page, `slipdock set-board --route
KIND=EMAIL[,EMAIL]` / `--no-route KIND`, `PATCH /api/boards/:board
{"wait_routes": {...}}` or `update_board` `wait_routes`; the rejection-limit
wait asks as `release`, and an audit disagreement is emailed to `release`'s
people. An agent can't
answer a wait it opened. A runner job may wait on its own card or any card
beneath it: an epic's pass asks about a subcard on the subcard, the job
parks, and the answer sends the epic again with the subcard named. `slipdock work` (`GET /api/work`) lists what is
waiting on you, and `whoami` counts it (`waiting_on_you`). See
[the manual](manual/waiting-on-a-person-waits.md).

**What in an epic's tree waits on you.** `get_card` and `get_board`
(`GET /api/cards/:id`, `GET /api/boards/:board`) carry `waiting_on_me`:
`count` (the items on you), `cards` (each the same item `slipdock work` /
`GET /api/work` gives, with `short`, its reason in a few words),
`on_others` (open waits in the tree on someone else) and `line`, the epic
tile's glance line. On a card it is the card's sub-board tree; on a board it
is the whole tree's, and each epic in the lists carries its own. `slipdock
card <epic>` and `slipdock board` print a `Waiting on you:` line. An epic
whose tree is all waiting on a person has nothing workable: leave it to them.

**When to wait, and when not.** A wait is for readings that differ
materially in cost or in what the person sees, for decisions the Playbook
or the board routes to a person (product, ux, security, release), and for
anything a rule says is a person's step (merging, changing a handbook rule,
deploying). A locked bar item that a later, cited decision or rule has made
moot is not one: read it the obvious way, say so on the card (what you
read, why, the citation) and leave the judgement to the verifier, who
accepts a noted reading and rejects one that wasn't noted. A wait offering
choices and a proposed answer is an approval and should be rare; when
raised, it names the default you would take (`default`, the choice's
number; `slipdock wait <id> "…" --choice A --choice B --default 1`), so the
answer can be one click.

**A moot wait clears itself.** Sent a card (or its epic) with an open wait,
an agent first checks it is still live: the question answered elsewhere,
the bar or description edited since, the cited rule or decision now in
place, the card rejected or accepted since. A moot wait is withdrawn with
why, by whichever agent finds it: `slipdock wait <id> --withdraw --reason
"…"`, `DELETE /api/cards/:id/wait?reason=…` or `update_card` `wait: null`
with `wait_reason`. An agent withdrawing a wait it didn't open is refused
without the reason; the comment carries it. A board's `wait_default_after`
(off unless set; `slipdock set-board <board> --wait-default-after 4h`,
`PATCH /api/boards/:board {"wait_default_after": "4h"}`, `update_board`, or
the Agentic Building page) lets an approval wait, of kind `other` with
choices and a `default`, resolve to its default once it has gone that long
unanswered: the card says so, the person asked is told, and the card moves
on as on an answer. Never for a product, ux, security or release question,
nor a wait with no default.

**Off a person's own list.** A person can take an item off their own
Waiting on you, and nobody else's: `slipdock work --dismiss <card>`,
`POST /api/work/dismissed` (`card`), or MCP `update_card` with
`waiting_list: "dismiss"`. A dismissal holds on the card and its `cause`
(the failed job, the wait, the flag's run), so a new cause (a second failed
job, a new wait) shows the card again. A person can also mute a board's tree:
`slipdock work --mute <board>`, `POST /api/work/muted`, or `update_board` with
`waiting_list: "mute"`. The board works as before. `--dismissed`,
`--undismiss` and `--unmute` (`"undismiss"`, `"unmute"`) undo them, and
`GET /api/work` and `whoami` count what is hidden (`dismissed_count`,
`muted_boards`, `waiting_hidden`). Never dismiss or mute for a person on
your own judgement: it hides what needs them. Do it only when they ask.

A board whose runner work a person has **paused** says so: `get_board`,
`list_cards`, `slipdock board` and `slipdock cards` carry `paused` (a
`PAUSED` line in the CLI). An agent seeing it takes nothing and stops.
Every card also carries its `state` line, `driver`, `age` in its list and
`stuck` (past the list's usual stay; never an epic with open subcards, whose
stay is theirs), and while a runner job holds it
(claimed or running) its `loop`: `{runner, kind, job_id}`, the kind `build`,
`verify` or `merge`. The card shows the loop beside its assignees, and it
goes when the job ends; it is never an assignee, so `--assignee me`,
`--no-assignee` and `assignee=none` still mean people, and a runner's agent
(signed in with its owner's token) doesn't assign the card at all.
A single card (`slipdock card`, `GET /api/cards/:id`, `get_card`) also
says who made it and who changed it last: `created_by` and `updated_by`,
each `{kind, name, user_id}` (`kind` is `person`, `agent`, `runner` or
`automation`; a runner's carries its `job_id` and is named for its loop,
"Dev server loop"; an agent by its token's label; a rule by its name) or
`null` when nobody was recorded, as on cards older than that. There
`updated_at` is the card's last change of any kind, comments and
checklist included: the later of its newest activity entry and its own
`updated_at`.
`list_cards` / `slipdock cards` filter on `stuck` and `driver`; `slipdock pulse <board>` (`get_board` with
`pulse: true`) gives the board's flow numbers, `slipdock flow <board>`
(`history: true`, `GET /api/boards/:id/flow?days=`) its flow day by day,
and `slipdock runner-stats <board>` (`runners: true`,
`GET /api/boards/:id/runner_stats`) how its runners are doing, and
`slipdock quality <board> [--days N]` (`GET /api/boards/:id/quality?days=`)
how well agent work goes: cards accepted on their first submission,
rejections per card by handbook area, job timeouts, failures, requeues and
give-ups per 100 jobs, health incidents fixed versus flagged, rejections by
part and by rule id, disputed `Handbook:` lines and audits (`--rules` lists
every broken rule with its page, what the triage card reads). A person sees
all of it on the board's **Visualise** page. A card's history — how
long it sat in each list and who moved it, its waits and its jobs — is
`get_card` with `timeline: true`, `GET /api/cards/:id/timeline` or
`slipdock timeline <id>`. See
[the manual](manual/flow-the-pulse-a-cards-state-and-its-age.md).

A board with **delivery metrics** on records its project's deploys from CI
(`slipdock deploy run --env production -- ./deploy.sh`, with the board's deploy
token in `SLIPDOCK_DEPLOY_TOKEN`) and reports the DORA numbers and idea to
production: `get_board` with `dora: true`, `GET /api/boards/:id/dora` or
`slipdock dora <board>`. A card a deploy named carries `shipped` (*Shipped to
production · 1a2b3c4 · 6 Nov 14:32*, the time in your time zone). An outage is an incident card tagged `incident`;
`slipdock incident-of <card> <deploy>` (or `POST /api/cards/:id/incident-of`)
names the deploy that caused it. To wire a repository up, `get_guide` with
`section: "deployments"` is the whole brief. See
[the manual](manual/delivery-metrics-deploys-and-dora.md).

**Step statuses.** The server posts a card's routine steps as its status
updates, so you needn't: an *On track* update with no user (shown as
*Slipdock*) when a build job is claimed (*Writing code*, or *Reworking after
verify failed* after a rejection), a wait opens (*Waiting for human*, or
*(rejection limit)* / *(held before merge)* for the server's own), the card is
submitted (*Verifying* with a verify pool, else *Waiting for human to
accept*), rejected (*Verify failed; queued for rework*), accepted on a
pull-request board (*Accepted; merging*), merged (*Merged*), completed
(*Done*), reopened (*Reopened*) and deployed (*Shipped to production*). The
same text is never posted twice in a row, and these notify nobody. Add your
own with `status_update` (MCP), `slipdock status <id> <health> "…"` or `POST
/api/cards/:id/status` only for what the server can't know, such as a risk.
A finished card's `get_card` and `slipdock card` show its **outcome** (done
when, accepted by whom, the merged PR) where the handoff was, and the handoff
written before it finished as `last_handoff`.

A card that repeats carries `recurrence` (its rule in words and when the next
is made). An agent sets one only when the person asked for repeating work:
`update_card` with `recurrence: {rule: "every mon"}`, `slipdock repeat <id>
"every mon"`, or `PUT /api/cards/:id/recurrence`. See
[the manual](manual/recurring-cards.md).

Card titles an agent writes stay short: about 60 characters at most, a series
as `<Series> <n>: <what>`, the detail in the description. A page for a card
sits in the card's folder, so its title needn't repeat the card's.

A snoozed card is hidden until a day: `list_cards`, `--deps ready` and the
board's lists leave it out until it wakes, so an agent never picks one up.
When the person says something can wait until a date, or what a card waits
for has one, snooze it rather than flag it `waiting`: `update_card` with
`snoozed_until: "2026-11-02"` (and `snooze_note`), `slipdock snooze <id>
<date> --note "…"`, or `POST /api/cards/:id/snooze`. See
[the manual](manual/snoozing-cards.md).

A person's **card views** say what they see of a card in the web app: each
element of its front and of the opened card, by global, board and list. They
are theirs alone, and your own output never follows them: `get_card`,
`list_cards` and the CLI give the whole card whatever they say. Change them only
when the person asks: `card_views` (MCP, by `action`), `slipdock card-view set
[--board B] [--list L] --show a --hide b`, or `PUT /api/card-views/level`.
`slipdock card-view applied --board B` (`GET /api/card-views/applied`) says
what a card there shows and which level decided it. See
[the manual](manual/card-views.md).

The **skills registry** keeps skills fetched from outside Slipdock (a GitHub
repository of `SKILL.md` files, or one file at an https URL), and a board can
hand one to its agents without anything installed. Add a source, read a skill
and enable it on a board only when the person asks: `skill_registry` (MCP, by
`action`), `slipdock registry add <url>`, `slipdock registry entry <id>` (the
whole file and its `content_hash`), and `slipdock registry enable <entry>
--board B --hash H`, or `/api/skill-sources`, `/api/skill-entries/:id` and
`POST /api/boards/:board/skills`. Enabling pins the text you read, so give the
`content_hash` the entry showed you; any other is refused. A source an admin
adds with `seed: true` (`registry add <url> --seed`) is everyone's; a new
server starts with `mattpocock/skills` as one, enabled nowhere. A refresh that
changes it marks it *changed upstream* and leaves the pinned text in place
until a writer reads the diff and re-pins it (`registry repin <name> --board B
--hash H`, `PATCH /api/boards/:board/skills/:name`). `slipdock registry
stages` (`GET /api/skill-stages`) lists the Playbook stages that name a skill
(`skill: <name>`) and what each gets. What a board's agents get is
`GET /api/boards/:board/skills`, for anyone who reads the board: each enabled
skill with its name, source, licence, pinned hash, `status` (`current`,
`changed` upstream, or `removed` from its source) and its pinned `text`, never
newer. The CLI's door is `slipdock skills board <board>` (with a name, that
one's pinned text), and MCP's is `get_guide` with `board`, which adds the same
list as `skills`. `slipdock-plan` uses it: for a stage that names a skill, the
one enabled on the board, else one installed locally, else its own text, and
it says which. See [the manual](manual/tools.md#skills-from-elsewhere).

The board gardener finds rot — epics done but open, cards stuck in progress,
duplicates, orphaned pages, mistyped links, and on a handbook board long
sections, broad `covers:`, `must` rules left to `judgement`, duplicate rule ids
and decisions that don't link back to the one they supersede — and proposes
fixes that a person approves. `garden` lists a board's open suggestions (`run: true` looks it over
first, which is a write: a read-only token can list but not run), and `garden_decide` applies, dismisses or undoes one with
`confirm: true`. Show the person the suggestions and apply only what they
approve; never dismiss one on your own judgment, since a dismissal is
remembered. The CLI is `slipdock garden <board> [--run]` and `slipdock garden
apply|dismiss|undo <id>`. See [the manual](manual/tidying-up.md).

Never take work from a **Triage** list (category `triage`; the guide marks
it `triage: for a person`). The code sweep (`slipdock tools install-board
sweep --board B`, or `install_tool` with `tool: "sweep"`) files what it finds
there for a person to triage, one area and one lens a night; nothing feeds a
runner from it. See [the manual](manual/tools.md).

Never take work from a **Scheduled** list either (category `scheduled`; the
guide marks it `scheduled: worked by feed rules`). It is where recurring agent
work lands: a recurring card's next instance is made there when the board has
one and the series names no list of its own, and the Sweep and Handbook Tools
put their daily cards there. Feed rules work it: each `list_top` rule on the
ready list gets a sibling on Scheduled with the same pool when the list is
made or given the category, so a card from it comes to an agent only as a job.
`list_boards` names it as `scheduled` beside `ready` and `done`, and a card
still there after the end of its due day is on its board owner's Waiting on
you (`scheduled_missed`). Set the category with `slipdock new-column B
Scheduled --category scheduled` (or `set-column`), `POST|PATCH
/api/boards/:board/columns` or MCP `create_list`. See [the
manual](manual/recurring-cards.md).

Agents propose handbook edits rather than make them, where a rule or a
decision is concerned: `POST /api/boards/:board/garden/proposals` (`slipdock
garden propose <board> <file.json | ->`) files an open suggestion of check
`proposal`, with an `explanation`, `steps` (`edit_section`, `comment` or
`file_page` only) and the `findings` and `cards` behind it. An
`edit_section` step names a `page`, a `section` (its heading path) and the
new `body`; its `base` is the section as it was, so applying it refuses a
section edited since. A proposal, and any suggestion with an `edit_section`
step, is a person's to apply, dismiss or undo: the API refuses an agent.
The server files one by itself when a finding's count reaches the board's
`findings_propose_at` (3 by default, 0 off): a rule on the `## Rules` of
the page covering the finding's cards (else Specification), `must` citing
a check the finding names, else `should`; only from lessons (an agent's,
a verifier's or an audit's findings), never from events such as health
incidents or failed merges. Accepting it promotes the finding; triaging the
finding (promote, dismiss, merge) closes it with a note, and reopening the
finding reopens it; see [the manual](manual/findings.md).

It also offers prompts, ready-made workflows the client lists in its own menu
(the **+** menu in the Claude apps, `/mcp__slipdock__<name>` in Claude Code),
each rendered with live board data: `plan-my-day`, `weekly-review`, `triage`,
`resume`, `leave-handoff` and
`tidy-board`. A `board` or `card` argument completes as the person types. A
connector caches the list: after an upgrade that adds one, disconnect and
connect again. ChatGPT's connectors don't show prompts. See
[the manual](manual/mcp-server.md#the-prompts).

And it offers resources, which the *person* attaches rather than the model
fetching: `slipdock://board/{code}`, `slipdock://card/{id}`,
`slipdock://page/{code}`, `slipdock://view/{board}/{view}` and
`slipdock://work`, each as Markdown. The list (`resources/list`) is My work,
the person's favourites and the pages pinned to their favourite boards. A
resource is read with the same access checks as the tools; one the token
can't read is "resource not found", the same as one that isn't there. See
[the manual](manual/mcp-server.md#the-resources).

`get_guide` gives the short guide — how to work a board, the reader's own
boards and lists — and ends by naming the other sections, each one call
away with `section` (`automations`, `wiki`, `endpoints`…, or `all`). The
whole guide is more than a client shows in one tool result. The short guide
describes the first ten of the reader's boards in full, names the next
twenty and counts the rest, and names five archived boards at most, so it
stays the same size however many boards someone has; `all` lists every one.

`update_card` also colours a card's cover (`color`) and each edge of its
front (`border_top`, `border_right`, `border_bottom`, `border_left`: a
palette name, `""` for none), sets what blocks a card and works its checklist (add
items, tick and untick them by the ids `get_card` shows; a new order is over
HTTP, `POST /api/checklist/<item_id>/move {"before": <item_id>}`, or `slipdock
move-check <item-id> --before <item-id>`); `move_card` takes
`board` to send a card, subcards and all, to another board; `list_cards`
takes `archived` (`exclude`, the default, `include` or `only`) and `full:
true` for every card as `get_card` gives it; and
`archive_card` puts a card away or, with `restore`, brings it back, as
`archive_board` does for a board you own. The deletes cannot be undone, so
each has to be meant: `delete_card` needs `confirm: true`, `delete_board`
(owner only) needs `confirm` set to the board's code, and `delete_list`
refuses a list that still holds cards unless `with_cards: true`. A token
confined to some boards cannot `create_board`. The read tools are marked
read-only, so a client can let them run without asking each time; the
deletes are marked destructive.

A client connects one of two ways.

**Signing in through the browser (OAuth).** This is how claude.ai and the
Claude apps (desktop, mobile) connect, and it needs nothing but the
address. In claude.ai: **Settings → Connectors → Add custom connector**,
give it a name and `https://your-server/mcp`, and press **Connect**. You
are sent here to sign in and see what is asking: approve it, or lower it
to read-only first, and you are sent back. A connector added once is
there in the apps too. Each connection shows up under **Account → API
tokens** as a *connected app*, named for the client; deleting it there
disconnects it. The connection keeps itself renewed while it is used at
least once every 90 days, so
there is nothing to paste and nothing to rotate. Any client that does
MCP's OAuth (discovery, dynamic client registration, PKCE) connects the
same way; for Claude Code, add the server without a header and run `/mcp`
in a session to sign in:

```sh
claude mcp add --transport http slipdock https://your-server/mcp
```

**A pasted API token** (Account → API tokens), for clients that take a
URL and a header. Make it read-only if the client should only look: the
read tools work, and the write tools answer that the token is read-only.
A token confined to some boards only sees those. In Claude Code:

```sh
claude mcp add --transport http slipdock https://your-server/mcp \
  --header "Authorization: Bearer <token>"
```

The Claude API's MCP connector takes the same URL with the token as its
`authorization_token`. IDE clients that take a URL and a header work the
same way.

claude.ai connects from Anthropic's servers, not from your browser, so a
connector only works with a server reachable from the internet over
https. If you self-host behind an allowlist, let in `160.79.104.0/21`.

## How an ask becomes a card

Every agent on a board writes a one-sentence ask up the same way, as the
guide's *Epics and subcards* says under **Card shape**:

- **One card** when the ask fits one sitting, one agent and one PR and
  was said in a sentence; an epic with subcards only when it doesn't.
  Never an epic with one subcard, nor subcards the person didn't imply.
- **Where:** under the epic it serves if there is one (search first);
  otherwise top level, without making an epic to hold it.
- **Three things in the description**, each in proportion: what, in the
  person's words; where, if known; and a **done-when** line, the stop
  condition the evidence answers. One or two lines; no Given/When/Then
  unless the board's Playbook asks for it.
- **Don't add** an estimate, priority, tags, a due date or an assignee
  unless the person said so or the board's convention does.
- **Don't repeat the repo's rules** (tests, every door, the handbook
  line): whoever builds it reads those from the handbook and the repo.
- **Two readings:** write the obvious one and note the other in the
  description; ask only when they differ materially, once, before filing.
- **A bar item made moot** by a later, cited decision or rule: read it
  the obvious way and say so. Not a wait.
- **Dependencies:** `blocked_by` means *can't start until*, not *should
  come after*: set it where a card builds on another's code, schema or
  decision, and use list position for mere preference. A one-card ask
  gets none unless the person said "after X". None on a simple board.

A board's handbook can override these: the `## Card shape` section of
its Playbook page wins wherever it says otherwise. It isn't a gate: one
sentence is the person's judgement that one sentence was enough, and
this only makes every agent's judgement the same.

## Planning an idea: the `slipdock-plan` skill

Asked to *plan* ("plan this", "I want to build…", "break this into cards",
"spec this out", "where do we start"), an agent with the `slipdock-plan`
skill follows the board's handbook **Playbook**. It is not used for "add a
card…".

1. It finds the handbook. Where there is none, it offers to install one
   (`install_tool` with `tool: "handbook"`) and works from the baseline seed
   it carries.
2. It reads the Playbook and sizes the ask by its `## Sizing`. A card-sized
   ask gets one card, shaped by `## Card shape`, and the skill stops there.
3. It runs the stages the size takes, in order: Grill, Spike, Decide,
   Principles, Spec, Cards for a system, and Grill, Spike, Spec, Cards for a
   feature. For a
   stage whose section names a skill (`skill: <name>`) it uses, in order: the
   one enabled on the board from the skills registry (its pinned text, from
   `slipdock skills board <board> <name>` or `get_guide` with `board`), else
   one installed locally, else the stage's own text in `slipdock-plan`, and
   says which. A stage whose output is already on the board is skipped.
   **Spike** runs only when an open question passes three tests: only
   building answers it (not a person, not reading), a "no" changes the spec
   (it says how), and a late "no" costs more than the spike, counting flow
   time and lane contention as well as rework. One that fails only the
   third gets its card first in build order instead; none pass, and the
   stage is skipped, said so. The agent proposes the candidates and a person
   confirms them (unattended, as one `product` wait on the epic). Each
   confirmed question becomes a `spike` subcard of the epic, its bar the
   question and what counts as an answer, with no paths. Planning then
   stops, with a handoff on the epic saying it resumes at Spec. A spike
   holds no lane and merges nothing: its answer is a page pinned to the
   epic, its prototype stays on its branch (see **Spikes** under Profiles).
   When the last is accepted, the server opens a `product` wait on the
   epic, "Spikes answered (#…): resume planning". A person resumes; the
   skill reads the answer pages and writes the Spec from them, and an
   *inconclusive* answer goes back to the person: another spike, the risky
   card first, or drop the feature.
4. It writes where the Playbook says:
   - Decision pages go in `Handbook/Decisions`, each with its context, the
     choice, the alternatives and why not, and where it was decided.
   - Principles are appended only when the person agreed to them; otherwise
     they go in as a garden proposal.
   - The spec is a page on the epic.
   - The subcards are made in build order, with `blocked_by` where one card
     builds on another.
5. When the Playbook's `## Defaults` names a page of the person's own
   defaults, the decide stage proposes each default and asks. A default is
   never imposed.

The skill adds no tools of its own: it uses the CLI or the MCP tools
(`read_page`, `write_page`, `create_card`). It never asks the server to plan.
Run unattended, it puts its questions in a wait instead of answering them
itself.

## The handbook's rules

On a board that keeps a handbook (`slipdock handbook <board>`), each
section page (Specification, Architecture, UX & UI, Components, Data model,
Shared modules, Testing & tooling, Operations, Principles, Playbook) lists
its rules in a `## Rules` section, one item each:
`- **UX-4** must · test/app_web/design_tokens_test.exs · No colour literals
in templates.` That is an id (the page's prefix and a number), `must` or
`should`, an optional `scope <globs>` (otherwise the page's `covers:`), the
check (a test path, or `judgement`) and the rule. An agent building a card
keeps to the rules that cover the files it touches, a reviewer cites them
by id, and an agent tidying a page leaves them as they are.
`slipdock handbook <board>` lists any item that doesn't read as a rule.

Two of the pages say how the project decides and plans (Handbook Tool
1.5.0). **Principles** are the tie-breakers between two right ways, each a
short paragraph and a `PRIN-n should · judgement` rule that covers every
path, so they come with the rules for any change. The **Playbook** is how
an idea becomes cards: when it applies, sizing, the stages, card shape and
the person's defaults. Only an agent asked to plan reads it; the server
never does when a card is made. A board makes both its own by editing them.

To get the rules for a change, ask with its paths:

```sh
slipdock handbook <board> --paths lib/app_web/live/menu.ex,priv/repo/migrations/x.exs
git diff --name-only main | slipdock handbook <board> --paths-from -
```

Over REST that is `GET /api/boards/:board/handbook?paths=a,b`. A card
whose lane has `paths` carries the same rules in `get_card`'s `handbook`
(`rules`, `must` first, cut to fit, with `rules_more`), and `slipdock card`
prints them in its Handbook block. The answer also lists the pages whose
`covers:` take the paths in (`pages`, each with how many), which is what a
reconcile reads for a range of commits.

A rule is a person's call. One a card adds, rewords or drops goes in as a
proposal (`slipdock garden propose`), not an edit. An agent's edit to a
rule is flagged anyway: the gardener's `rule_changed` check compares each
page's rules with the last version a person approved and suggests putting
them back, which the person applies, or keeping them, which they dismiss.

## Let the board send it work (runners)

Everything above is an agent you start, that then reads the board. A
**runner** is the other way round: the board sends a card to an agent on a
machine of yours when something happens — a card arrives in a list, say —
and the agent works it and reports back. You set one up from the board, under
**Automations → Connect a runner**, which asks where the work should happen
and gives you exactly what to paste:

| Scenario | What you paste | Costs while idle |
| --- | --- | --- |
| Linux / macOS machine | `curl … /runner/install.sh \| sh -s -- --url … --token sdr_… --pool …` — the shell runner (`sh` and `curl` only) as a systemd user service or launchd agent | nothing |
| Windows machine | `& ([scriptblock]::Create((irm '…/runner/install.ps1'))) -Url … -Token sdr_…` — the PowerShell runner, started at logon by Task Scheduler | nothing |
| Claude Code on my machine | `claude mcp add …`, the skills, and a `/loop /slipdock-loop … taking a job from the … pool's queue` line | a Claude turn per check |
| Claude, scheduled | a Claude Desktop local routine, or a cloud routine at claude.ai/code/routines with the Slipdock connector | a Claude turn per run |
| ChatGPT | the Slipdock connector in ChatGPT, and a prompt for a chat or a scheduled task that takes one job with `claim_job`, works it in the conversation and ends with `finish_job` | a ChatGPT turn per check |

It can also add the rule that sends a list's cards to the runner's **pool**
(the *Send cards to a runner* preset, offered once the board has a runner,
with an optional prompt for what each job is told) —
or one that works a list **top card first, one at a time** (*Work a list with
a runner*, trigger `list_top`): whenever nothing it sent is still open it
sends the top open card nobody has taken, skipping blocked, waiting and
dependency-blocked ones and any with a job already open on it (so two such
rules for two pools work one list side by side), and, with lanes holding,
any whose paths overlap a card in progress: a queued job of its own that a
lane holds is withdrawn and the next card that could start sent instead,
the held card keeping its place for when its lane frees, so a runner can take over from a `/loop` or cron
pass working the To Do list. Its jobs **wait while anything is in progress**
(`wait_while_doing` on the `runner` action, ticked by default for that rule):
a queued job isn't handed out while another open card that a runner job
is working on (a job queued, claimed or running on it or its epic) sits in
an in-progress list on its board, and the job listing says why
(`waiting_on: "#123 is in progress"`). A card in progress with no open job,
one somebody moved there by hand included, holds nothing back. A card its job leaves in progress goes back to the top of the
list for another try (`requeue_stuck: N` on the `runner` action, 1 by
default for that rule), then is flagged blocked and left there, so an agent
pass never has to recover its own card. A rule with the trigger
`job_finished` (`outcome`: done, failed, cancelled, timeout, requeued,
gave_up) hears each job end once, with `{{job.*}}` placeholders, so alerts
on a stalled loop come from the board rather than a hook. The board's owner
can **pause** the tree or one pool with a reason (`slipdock pause <board>
[--pool P] --reason "…"`; agents may pause, only a person resumes with
`slipdock resume`), and with **WIP limits hold automated work** on
(`slipdock set-board --automation-wip`) a full first in-progress list holds
jobs too. A held job names one reason: paused, WIP full, a card in
progress, or no runner online. While a job runs, its runner sends the agent's
transcript about once a minute, so the job has a **live log** on the server
(`GET /api/jobs/:id/transcript`, JSON Lines, tokens taken out), watched on the
card and the Runners panel, with `slipdock job <id> --follow`, or the MCP tool
`job_log` (`GET /api/jobs/:id/log`, one line per message or tool call). A log is
deleted a set time after the job ends (the board's `job_log_hours`, 24, or
`failure_log_hours`, 168, for a failure) unless kept: `slipdock job <id> --keep`
or `keep_job_log` writes it as a `Pass <card> (<date>)` page in the card's folder. It takes standing instructions
and before/after hooks, written into the config or prompt it generates; for the
site-specific part of a hook (which notifier, what to keep from a pass) it gives
a prompt to paste into Claude Code on that machine (*Have Claude write this
hook*, or `slipdock runner setup <board> <runner> --hook-prompt`), which states
the hook contract and points at a worked example served at
`/runner/examples/after-job-hook.sh`, with a pass-log script at
`/runner/examples/passlog.sh` that writes `Pass <card> (<YYYY-MM-DD HH.MM>)`
into the card's folder. The pass log is opt-in (`SLIPDOCK_HOOK_PASSLOG`): a
job's log is kept with Keep this log instead.

Runners also report **drift**: on every claim the SHA-256 of each installed
slipdock skill's `SKILL.md` and of the `slipdock` CLI, which the server
compares with what it serves. `slipdock runners` (SKILLS · CLI), the Runners
panel and the runner's `drift` in the API say current, drifted (naming the
skills), old or unknown, and a drifted runner raises one alert until it is
current again. A runner that keeps itself current installs the server's
skills before each job (see *One source for each skill* under §3 above),
so it doesn't stay drifted; anywhere else, run the install one-liner again.

**A job runs with nobody watching**, so two things are set up for it. A
Claude runner may use the Slipdock MCP tools without asking (`--allowedTools`
for the servers named in the wizard — `claude_ai_Slipdock`, the claude.ai
connector, and `slipdock`, one added with `claude mcp add`, by default):
without that it can't read the card or write anything back. Untick **Let it
use the Slipdock tools** and it has no access to the board. And every job's
prompt ends by saying nobody will answer questions: choose inputs from the
card, say what was chosen, or open a wait saying what it needs and stop
(the job is **parked**, its card goes back on top of the list so the next
one runs, and the answer sends the card to the rule again with the answer
on top of the prompt, ahead of a next card's job nobody has taken yet); if
the board is paused, finish the card and take no
other; and
to leave a handoff (`leave_handoff`) whenever it stops with the card
unfinished. A job that ends with its card still open, and no handoff written
during it, leaves its summary as the card's handoff. Give
the runner a **working directory** — the project's folder: Claude Code loads
a project's own commands, skills and `.claude/settings.json` only from the
directory it starts in, and the wizard warns while it's blank or still the
default `/tmp`.

**The trust line.** Runners pull: they dial out and ask for work, and the
server never connects to them, so nothing needs a port, a tunnel or an
exception to the address rules webhooks live by. And the server sends only
data — a job's id, its kind, the card and the prompt. What each kind of job
*runs* is written in the runner's config on its own machine, and a kind with
no definition there is refused without running anything. A rule can pick the
kind; it can never pick a command. A runner's token (`sdr_…`) works only for
taking and reporting on its own pool's jobs.

**ChatGPT** has no repository or shell, so its prompt has it do the work
in the conversation (writing, research, planning) and hand back, with the job
finished `failed`, a card that needs a machine; commit and push can't be
ticked for it, and hooks are left out. Its jobs are of kind `chatgpt`, so a
rule can send it only the cards it can finish — give it a list or pool of its
own.

A Claude or ChatGPT session takes jobs from the same queue with the token it already
has — the MCP tools `claim_job`, `job_progress` and `finish_job`, or
`slipdock claim-job` — so a `/loop` and a shell runner never work the same
card. `job_progress` with `step` (`slipdock job-progress --step`) says what a
job is doing now on the job alone, not the card: a verify job reports each
step that way, and every runner job's prompt asks for its milestones too (on
an epic, each subcard as it starts, is submitted and merges). Every step is
kept on the job with its time. The card's own chat (*Ask AI about this card*)
reads that record for a person: every job on the card and its subcards with
its steps, exit status and summary, the timeline, waits, handoffs, comments,
and the bar, evidence, rejections, audits, merge and deploys. It also works
out where a card's time went (`card_lead_time`): its lead time by phase, from
the ready list (and which jobs held the pool) through build, CI, verify and
merge to deploy, with what it can't explain as a phase of its own, and what
its jobs spent by phase (model and tool time from their logs, and tokens
where a log carried `usage`; no prices). And it
reads a job's log, summed up first (what the agent said, model and tool time
by kind, the longest and the failed calls, each by line) and then any stretch
in full, while the log lasts. CI is read
from the `Build started` / `Build failed` / `Build passed` comments and from
steps that mention CI, so write those as they happen: a failure reported only
after its fix is pushed reads as one CI span with the fix inside it. So a step
that says what happened (*CI red: credo*, *#1876 submitted*) is what answers
*why did it fail?* and *where did the time go?* later. The epic's
comments are the server's to keep: it posts a line on the epic as each
subcard starts, is submitted, rejected, accepted, merged, fails a build,
waits on a person or ships, with the done count, and keeps the epic's %
complete following its subcards. An agent comments there only what the
server can't know: decisions, surprises, dead ends and changes of plan. The agent a
runner started may report on the runner's job (the CLI sends
`$SLIPDOCK_JOB_ID`), though only the runner claims and finishes it. The details, and the HTTP protocol a runner speaks, are in
[the manual](manual/runners.md) and the guide's *Runners* section.

**The health monitor.** Every few minutes the server looks for work stuck
in ways only a person would otherwise notice — jobs nobody takes, deadlocks,
verification and merges that stall, cards and waits nobody is moving — tries
a safe fix (a comment on the card each time), and flags what it can't fix: the
card gets the `stuck` flag, or the board an alert. A card flagged `stuck` is
for a person; an agent says on it what it knows and leaves the flag alone.
`slipdock health <board>`, the board's Health page and
`GET /api/boards/:board/health` show the incidents; see
[the manual](manual/the-health-monitor.md).

**Right now.** What is happening on a board's tree at this moment — each
runner and the job and step it is on, every card in progress with its board,
list, parent epic and what holds it (`waiting`, `verifying`, `merging`,
`blocked`, `review`, `stuck` for the health monitor's flag, or `over_usual`
for one merely past its list's usual stay), and the jobs queued with why each
is held — is the board's Right now page (`/boards/:id/now`, one click from the
board page's pulse line, or its own line, with Agentic Building on),
`slipdock now <board>` (`--json` for the JSON), `GET /api/boards/:board/now`
and MCP `get_board` `now: true`; see
[the manual](manual/right-now.md).

**The overseer.** A board's owner can turn on an eye on outcomes
(`slipdock overseer <board> --on`): server checks, every minute, for work
going round (a second rejection, a third runner pass), a board waiting only
on a person with nothing running, cards slower than the board's P85 for
their profile and jobs whose step hasn't changed in 30 minutes, idle runners
beside a full ready list or jobs queued behind one lane, and epics whose
open subcards are all blocked. Each fires once, as an alert and an email
with why and what to do, heads the owner's `slipdock work` and `whoami`
(reason `overseer`), and clears itself when it ends. A runner job of kind
`overseer` (only to a runner whose config has `job_overseer`, on a cheap
model) is handed those conditions and the pulse in its prompt, and nothing
else: it reads nothing more, takes no action, and answers with one line of
JSON, `{"health", "digest", "look_now"}`, kept as a status update on the
board's *Overseer* card. Passes come every 10 minutes while cards are active,
longer when little or nothing is in flight. `GET`/`PATCH
/api/boards/:board/overseer` (reading needs read on the tree's root, not
just the sub-board named), MCP `get_board overseer: true` and
`update_board overseer: {…}`; see [the manual](manual/the-overseer.md).

**Findings.** What a pass learned that the code doesn't show goes on the
board, not in one machine's agent memory: a `Findings:` block in the closing
comment, once (on a board that verifies work, the completion's evidence; never
repeated in a wrap-up or on the epic), beside the `Handbook:` line, one
`- kind: text` item each (`gotcha`, `rule`, `handbook-wrong`, `tooling`,
`process`, and `tooling (runner)` for the machine's own CLI or skills, kept
with the runner), or `Findings: none`. A lesson said again is counted on the
finding it repeats, on this card or another (`rule` and `handbook-wrong`
excepted across cards). An item already dealt with says where, and is kept
*promoted*, not open: `- gotcha [done: W-1950 §Local setup]: …` when it is
settled in the handbook, `- tooling: … → #2087` when a card was filed for it.
A fix is a card, not a finding: a concrete change you could hand to someone
(a missing test such as "no test pins `slipdock done`'s exit codes", a stale
moduledoc or doc entry, a tooling bug such as "`page section --append -`
writes a literal `-`") goes on the board as a card now (`slipdock add <board>
"…" --desc "…" --column Backlog`) and into the block as `→ #<card>`. A
finding is only for what is uncertain, cuts across cards, or shows the
handbook wrong ("`mix format` can need two passes", "the shared `_pre_push`
database can hold another branch's migration", "W-1950 §Tests says async is
safe, but the fixture is one user").
The test
for one: would a card on a different subject want to know this? Never a
pointer (`in the evidence`, `recorded on #1819`), an event the board records
itself, something the card fixed, or a fact about the card's own code
(`Boards.move_card/4 returns :ok`); `Findings: none` is the usual answer.
A block that only points elsewhere records nothing: the evidence is a comment
of its own, and its block is read there.
Settled knowledge goes straight into the handbook. The server records
its own (rejections, timeouts, requeues, failed merges; a lane refusal is
not one), and the daily triage and the server handle them: they merge,
promote and dismiss findings, and draft a rule as a garden proposal when one
recurs. Those proposals are what wait on a person, so the board's Findings
page (`/boards/:id/findings`, from the board's Agentic Building page, whose
tile counts them; a card links there when it has open ones) leads with them,
as `slipdock findings` (each by id), `awaiting` in
`GET /api/boards/:board/findings` and MCP `garden` with `findings: true` do.
The findings below them are reference, triaged by hand when wanted with
`slipdock findings <board>`, `slipdock finding <id> promote|dismiss|merge
--into <id>`, `GET /api/boards/:board/findings`; see
[the manual](manual/findings.md).

**The ledger.** What shipped on a board tree since a time, for a person to
skim instead of approving each card: each card completed, accepted, merged or
deployed, with who accepted it (`accepted_by`: a person or an agent; `audit`
the last audit's verdict), the first line of its `evidence`, the `should`
rules its verifier marked broken (`should_broken`), its `pr` and `deploys`,
its `lead_time` by phase with what its jobs spent (`cost`: `model_seconds`,
`tool_seconds`, `jobs`, and `tokens` only when known), an epic's `subcards`
rollup and the card's `url`
(its panel, at the chat), grouped by day. `slipdock ledger <board> [--since
S]`, `GET /api/boards/:board/ledger?since=`, MCP `activity` with `view:
"ledger"`, or the board's Ledger page (`/boards/:id/ledger`). `since` is days,
a date or an ISO time; without it, 07:00 yesterday in the board's timezone.
It writes nothing. See [the manual](manual/the-ledger.md).

**Incidents.** When a person tells you a card broke something that shipped,
file it (or edit it) as an incident: `caused_by`, the card whose shipping
caused it (any card you can read), and `missed_by`, the check that should
have caught it (`bar`, `rules`, `ci`, `verify`, `audit` or `none`).
`slipdock add|edit … --caused-by 123 --missed-by ci` (`--no-caused-by`,
`--no-missed-by` clear them), `update_card`/`create_card` `caused_by` and
`missed_by`, or `PATCH /api/cards/:id`. An unknown layer or a card you can't
read is refused with a sentence. While both are set the causing card carries
one `process` finding with source `incident`, kept in step as they change
(`slipdock findings <board> --source incident`). Set them only when told: an
incident is a person's judgement. See [the manual](manual/incidents.md).

**Verified work.** A board can check what its agents finish, with each
check off until it is turned on (the board's Agentic Building page, or
`update_board`): a **bar** written
before work starts, which then locks (best written by whoever files the
card: `create_card` and `slipdock add` take `bar` and `paths`, so a planned
card is one write, checked as on an update, and best phrased so the builder
can meet it: a rule change "proposed as a garden proposal (rule id,
wording)", never "W-x has rule Y"; the builder checks it at pickup and asks
with a wait when a part needs a person); **evidence** when a card completes
(or is created already done; a bare `-` as the evidence is refused on any
board, since it is what a client that doesn't read stdin sends for
`--evidence -`: pass the text, or pipe it from a CLI that reads stdin);
and a **second agent** who accepts the work or rejects it with the reason.
With a verify pool set, each submitted card is queued as a `verify` job.
On a board that ships by pull request, its CI is the one full test run: the
builder runs only its own tests before pushing, and the verifier checks the
pull request's checks at the submitted commit rather than running the suite
again. A card tagged `security` ships a neutral pull request: the title
`Maintenance (#<id>)` rather than the card's, a body of only the card id, and
commits that describe the change in general terms, never the hole; the
detail stays on the card until it deploys (`shipping.neutral` in
`get_card`).
The verifier judges four things, in order: **the ask** (does the bar cover
what the card asks for? a bar that leaves part out is a rejection), **the
bar**, and on a board with a handbook **the rules** for the diff's paths
(`git diff --name-only` from the merge base piped to `slipdock handbook
<board> --paths-from -`; a broken `must` is a rejection) and **the
`Handbook:` line**, held against the docs gate (`no change` on a diff that
needed an update is a rejection). A rejection cites the check it fails: a bar
item, the ask, a rule id or the Handbook line. **On a bug, the ask is the
reported symptom**: the check is would the reporter now see it fixed, not
does the work meet the bar. The builder reproduces the reported symptom on
the reporter's scenario and posts the repro as its own comment; a clean repro
that doesn't show it opens a wait saying what was seen and asking for a
screenshot or steps (which screen, which control), never conditions built
until something fails. The verifier rejects (`the ask: …`) a bug card whose
card or evidence says the reported symptom or its cause was never seen,
however good the tests. A rule being a person's call,
a bar item that adds, rewords or drops a handbook rule is met by a matching
open rule proposal (an `edit_section` step on that page's `## Rules`;
`slipdock garden <board> --check proposal`): the verifier judges the
proposal's content, not the live Rules list, and names its id when it
accepts. A rejection never asks the builder to edit `## Rules` directly,
only to file or correct the proposal; an audit judges the same way. The
builder runs the same checks before submitting. The verdict is kept in parts on the card
(`verify_checks`: the ask, each bar item, the suite, each rule and the
Handbook line), given as `checks` to `verify_card` or `POST
/api/cards/:id/verify`, or `slipdock verify … --check bar:2=fail:why`
(repeated, or `--checks-file`). A rule broken only in lines the diff didn't
change is `rule:<id>=pre-existing:<file>:<line>`: never a rejection, kept as a
`rule` finding on the card (source `verification`), and shown apart from passed
and failed parts. **A rejection names every instance found**: once the
verifier finds a rule broken, it looks for every other instance of the same
break the card could have missed (the same list, the same string, the same
door) and names them all in one rejection, each as its own line under the one
rule with its file and line (`--check rule:SPEC-10=broken:README.md:40:why`,
repeated), and says in the reason that it looked. A rule broken in several
places is one failing part, and the rejection's comment lists its instances
under it. A rejection names at least one failing part;
an acceptance with a broken `must` rule (or any other failing part) is
refused. The card panel and `slipdock card` list the parts under
Verification; a later decision replaces them, and each decision's comment
keeps its own. A card resubmitted after a rejection is judged on what
changed: the verify prompt carries the last verdict and the commit it judged,
the verifier judges the parts that failed and any part the commits since touch
(`git diff --name-only <then> <now>`), and a part that passed then and isn't
judged again (`--check bar:1=carried`, or left out) is carried, shown as
*carried from <sha>*. A failed part can't be carried; an audit carries
nothing. The builder's resubmission evidence names the rejected commit and
what changed since. A card's second rejection, or one for a rule id an earlier
rejection named, marks it as going round in circles: it stays flagged `review`
(a rejection otherwise takes the flag off) until it is accepted, a *Going
round in circles* comment lists the rounds and the parts each failed, a
warning alert goes up on the root board and the board's owner (and whoever
`release` questions go to) is emailed, and it heads the owner's `slipdock
work` (reason `circling`) and counts in `whoami`'s waiting. The runners still
send it for rework; the flag isn't a stop. A failed merge counts towards the
two, but only a verifier's rejection fires it. A board's `verify_rejection_limit` (2 by default, 0 never;
`slipdock set-board --verify-rejection-limit`) sends the rejection after that
many to a person: a wait on the board's owner, *Rework as rejected* or
*Accept as is*, with the card flagged `waiting` so runners pass it over. The
wait lists the parts that failed in each rejection and asks whether the
approach, not the fix, is wrong. An
agent never answers it. A board's `verify_audit` (1 in N; 0, the default,
none; `slipdock set-board --verify-audit N`) checks the checker: about one card
in N that an agent accepted is queued to the verify pool again as an audit, a
`verify` job marked `audit`, never to the runner that built it or the one that
verified it (on a pull request board, once it has merged). Its prompt shows
the original verdict and has every rule judged, `should` ones too. The audit
changes nothing: `slipdock verify <id> agree|disagree --reason …` (or
`verify_card`) is a comment, and a disagreement raises an alert for the board's
owner. The acceptance stands.
The installer's config gives every runner a `job_verify` that runs the same
agent on the server's prompt, without the standing instructions, so a runner
can check another runner's work. Deciding is `verify_card` or `slipdock
verify`, and never on a card you submitted yourself. A board can also
**ship by pull request**: its agents push a `card-<id>` branch and open a
pull request, never the default branch, and complete with its URL
and head commit (`slipdock done --pr URL --evidence-commit SHA`; a PR
without its commit is refused, on a resubmission too). An epic there names none of its own: its subcards
each ship and merge theirs, and once they are all merged the epic completes
with `slipdock done --evidence "…"` and no `--pr`, and is accepted with
nothing to merge. A card that changes no code (a sweep, a handbook
reconcile, a read-and-file card) has no pull request either, and never a
token one: it completes with `slipdock done --no-code "<why>"`
(`complete_card` `no_code`), and accepting it merges nothing. The claimed job's prompt and the card itself
(`get_card`'s `shipping`) say so, so a runner needs no setup for it, and
both runner scripts have a built-in `merge` kind that merges the accepted
commit's pull request in their own repository (`MERGE=0` turns it off;
runners installed now replace themselves with the server's newer script
between any two jobs, after an empty claim or after a job's finish and
before the next claim, on a matching checksum, so new kinds reach them
however busy the queue is):
accepting a card there queues the merge, and the merge completes it (a
failed merge sends it back rejected with the reason). The merge goes to a
runner that is idle now, else to the one that accepted the card, so it
doesn't wait for a pass to end; a runner that can't merge in that
repository hands it on rather than failing the card. The skills
(`slipdock-loop`, `slipdock-work`) say what changes in a pass; see
[the manual](manual/verified-work.md).

**Epics close over finished subcards.** On every board, with no switch, an
agent can't complete (or submit) a card while its sub-board has open cards
(not done, not archived; one awaiting verification counts as finished), by
`complete_card`, `slipdock done`, `PATCH /api/cards/:id` or a move into the
done list. The 422 or tool error names them (`#12 Foo, #13 Bar are still
open`), so a pass that missed subcards added while it worked finds them
there. A person can always close it.

**Done stays done.** On every board, with no switch, an agent can't reopen
a completed card: unticking it (`slipdock undone`, `PATCH /api/cards/:id
{"completed": false}`) or moving it out of the done list (`move_card`,
`slipdock move`) is refused with a 422 or tool error, and the card stays
done. Nothing in a pass needs it: a rejection comes before Done, a retry
only puts back a card left in progress, and a recurring card is copied. A
script that does it undoes finished work, as a runner hook putting back a
card it thought stuck did while the card's merge was finishing. A person
reopens finished work; if a done card needs more, add a card for that and
link it.

**Lanes.** Agents side by side in one repository stay out of each other's
files, each part optional and off by default: a card's `paths` (globs, set
with `update_card` `paths` or `slipdock edit --paths`, or when the card is
made: `create_card` `paths`, `slipdock add --paths`), a board switch
(`lanes`) that refuses an agent starting a card whose paths overlap one in
progress, naming it (a person moving the card overrides it), a runner
setting that runs each job in a git worktree of its own (`--worktree`), and
a pre-commit hook a person installs (`slipdock hook install lane-check`)
that refuses a commit staging files outside the card's paths. The skills
write the paths before starting, stage only them, and use a worktree when
another session shares the repository. On a board that verifies work and
ships by push, a card awaiting verification frees its lane and stops
blocking its dependents until a rejection; on a pull request board it keeps
both until the merge. An epic's lane is its subcards': in progress it holds
none of its own, and it waits only when none of its subcards could start.
A board's `shared_paths` (`update_board` `shared_paths`, `slipdock set-board
--shared-paths`) are globs that never count toward a lane: declare those
files honestly, and an overlap only inside them holds nobody. A path only
partly inside one still counts. `get_card` and `slipdock card` mark a
card's shared paths, the job's prompt names them, and the lane-check hook
lets them through; keep to your own sections of a shared file and rebase
before pushing. A board's `lane_mode` is `off`, `hold` (what `lanes: true`
means: overlapping starts refused, jobs held) or `advise` (`update_board`
`lane_mode`, `slipdock set-board --lane-mode advise`): under `advise`
nothing is held, and your job's prompt carries a *Lanes* block naming each
card in progress whose paths overlap yours. Read that card and its branch
before editing those files, stay out of them where you can, and rebase on
the default branch before pushing.
Only a card a runner job is working on holds a lane: one in progress with
no open job, dragged there by hand or left behind, holds none. Nor does a
`spike`, whose code is never merged. Lanes hold work jobs only, never a verify or merge
job. See [the manual](manual/lanes.md).

**Profiles.** On a board with `profiles` on (`profiles: on` on its line
in the guide), a card an agent claims or starts with no profile gets one
word inferred from its paths and tags, strictest first: `security`,
`schema`, `spike` (by tag only), `fix` (tagged `bug`), `docs` (every path
is documentation), else `feature`. Write a card's paths before starting
it so the inference has them. Set or clear the profile with `profile`
(`update_card`, `create_card`, `slipdock edit --profile`, `--no-profile`).
It shows on the card and on its ledger line (`card.profile`), with where
it came from beside it (`card.profile_source`): `inferred`, or who set it,
`person`, `agent` or `rule` (nil with no profile, or on a card older than
the field). The web panel shows a card with none what it would be inferred
as, for a person to take or override before an agent starts it. When you
complete the card, give the change you made: `slipdock done
--diff-base origin/main` (or `--changed-lines N --changed-files a,b`;
`complete_card` `changed_lines` and `changed_files`). A migration raises
the profile to `schema`, a security path to `security`, and more than 400
changed lines a `fix` or `docs` card to `feature` (unless a person set
it); never lower, with the reason in the card's activity.

**The human tier.** Each profile has one (`profile_tiers` in the board's
JSON): `none` (`docs`, `fix`, `spike`) and `ledger` (`feature`) let your
acceptance merge as usual; `before_merge` (`schema`, `security`) holds
it on a board that ships by pull request. Accepting such a
card as a verifier leaves it `verify_state: "held"` with a `release` wait
(Merge / Send back) for a person, and no merge job: your verify job is
done once you have decided. You can't answer that wait or decide a held
card (`403`). A card sent back comes to the ready list as a rejection,
the person's reason under *Verification*: rework it as any other. Change
a tier on the root board: `slipdock set-board B --profile-tier
schema=none`, `update_board` `profile_tiers`. See [the
manual](manual/profiles.md#the-human-tier).

**Spikes.** A `spike` card (profile `spike`, or no profile and tagged
`spike`, on any board) answers a question by building, and its code is
never merged: the prototype stays on its branch and any pull request is
closed. Complete it with why instead, naming the answer's page and the
branch: `slipdock done ID --no-code "spike: answer on W-…, prototype on
card-ID"` (`complete_card` `no_code`). Naming a pull request is refused,
and accepting it merges nothing. It holds no lane, even with paths: an
overlapping card starts beside it, and no job waits for it.

**The verifier's spend.** With profiles on, completing a `docs` card on a
verifying board queues no verify job: the server accepts it (*Accepted by
the server*, `verify_checks.not_verified: "docs"`, your evidence's suite as
the suite) and merges or holds it per its tier, so give CI's result as
`--suite`. A failing suite sends it back. The bar is still required. As a
verifier of a `schema` or `security` card, your prompt has a defect
review: read the diff for bugs, give each finding with its file and line
(`--check defect:important|nit|pre-existing=<file>:<line>[:why]`), and
reject on any Important one; a Nit or a Pre-existing finding is reported
only. On a `fix`, `feature`, `schema` or `security` card your prompt also
has a mutation review: break 3 to 5 of the lines the diff added or changed
(on a `fix`, one undoes the fix), run only the card's tests against each,
restore it, and give each as `--check
mutant:killed|survived|pre-existing=<file>:<line>:<mutation>[:the missing
test]`, or `--check mutants=n/a:<why>` when nothing is worth mutating
(kept as `verify_checks.mutants`). A survivor on a changed line is a
rejection naming the test to write; a `pre-existing` one, in lines the
diff didn't change, is kept as a finding; a killed one is carried to a
resubmission unless its line changed. `slipdock quality` counts the
surviving-mutant rejections as a part. A claimed job carries the card's `profile` (MCP `claim_job`, the
REST claim's `job.profile`, the runner's `x-card-profile` header), and a
runner's config may set `MODEL_<profile>` to run that profile on another
model. See [the manual](manual/profiles.md#the-verifiers-spend).

## If you self-host

Two things to get right, both about the address:

- **Tell the app its own name.** `PHX_HOST`, and `SLIPDOCK_URL_SCHEME=https`
  with `SLIPDOCK_URL_PORT=443` if you are behind a TLS proxy (see
  [Running it](manual/running.md)). The guide and the installer hand out URLs
  built from this; get it wrong and every agent you set up is told to talk
  plain http to a port nobody is listening on.
- **The agent has to be able to reach it.** An install bound to a tailnet means
  the agent must be on that tailnet too — which rules out cloud agent sessions,
  and is a good reason to run yours locally. A server on a LAN address is the
  same problem.

Your co-users do not need anything you have: they set an agent up from the
**Set up an agent** page exactly as described above, and it points at your
server because that is the server that drew the page.

## When it goes wrong

| What you see | What it means |
| --- | --- |
| `not signed in` | No token. Run `slipdock auth`, or make one under Account → API tokens. |
| `could not reach …` | Wrong address, or the server is down. `slipdock url` says which address is in use; for a tailnet install, check the agent is on the tailnet. |
| An agent reporting `http://` URLs, or a redirect loop | The server has not been told it is behind TLS. Set `SLIPDOCK_URL_SCHEME=https` and restart. |
| `this API token is read-only` | Deliberate: that token was made for reading. Give it a read/write one if you mean it to write. |
| `this API token's scope doesn't allow it` | The token is confined to certain boards, or you asked an ordinary token to administer the server. |
| `card_limit_reached` (402) | The board owner's allowance of items — cards, pages and files together — is used up. Archive something finished with; a wiki page instead of a card will not get round it. |
| `trial_expired` (402) | A free trial has ended. Everything there stays readable and editable; nothing new can be added until there is a subscription. |
| A runner says `the server refused this runner (HTTP 401)` | Its token was revoked or replaced. **Setup → Make a new token** on the board, then run the one-liner again on that machine. |
| A runner job sits `queued` | No runner of that pool is running for that board: check its name and pool in **Automations → Runners** (*last seen*), and that the rule's pool is spelled the same. |
| A runner's agent says it can't use the Slipdock tools (`get_card`, `comment` refused) | The runner's claude line has no `--allowedTools` for the server, or names it wrongly. Its name on that machine is in `claude mcp list` (the claude.ai connector is `claude_ai_Slipdock`). **Setup**, tick *Let it use the Slipdock tools* with that name, and run the one-liner again; or set `ALLOWED_TOOLS` in the config by hand. |
| A runner's agent can't find a project command or skill (`/genarticle` "not found") | The runner has no working directory, so jobs start in your home and the project's `.claude/` isn't loaded. Set the working directory to the project's folder and run the one-liner again. |
| Every job fails with `cd: can't cd to ~/…` | A runner installed before `~` was understood wrote it in quotes, where sh doesn't expand it. Run the one-liner again (**Setup**), or give a full path. |
| A job fails with exit 127, "no such job kind" | The rule queued a kind this runner's config has no `job_<kind>` (shell) or `Job-<Kind>` (PowerShell) function for. Add one, or change the rule's kind. |
| Someone says they emailed a card or a page in and nothing happened | `slipdock inbound log` (or `GET /api/inbound/log`) says what each message made, or why it bounced or was ignored — see [Emailing your board](manual/emailing-your-board.md). A `+ Title` mail bounces when no page has that title (the log shows the near matches it offered). Their addresses are `slipdock inbound <board>` (a wiki folder's own: `--folder <path>`); don't `--rotate` it unless asked, since the old one stops working. A reply to a notification email (kind `reply`) bounces when it was all quote, came from another address, or the card is gone — see [Replying to a notification](manual/emailing-your-board.md#replying-to-a-notification). A `[#42] …` subject to a card address comments on card 42, and bounces when 42 isn't on that board or its sub-boards. |
| A rule meant to act on mail (`card_emailed`, `page_emailed`) didn't | It fires only for what mail made, once the message accepted (`slipdock inbound log`), so a card typed in by hand doesn't set it off. Its `column`, `folder` (a path, as `Notes/Calls`) and `how` (`new` or `added`) must match. Its last error is in `slipdock automations <board>`. A `page_emailed` rule can only flag, tag, prioritise, date or assign the page (or email, alert, log, call a URL, create a card): the rest is refused when it is saved. See [Rules for what mail brings in](manual/automations-and-alerts.md#rules-for-what-mail-brings-in). |
| The agent inventing list or tag names | It has not read the guide, or read it without a token. The guide with a token ends with your real boards and lists. |

## Where the pieces live

For anyone reading the code rather than using it:

- `priv/skills/` — the skills, served by `GET /api/skills` and
  `/api/skills.tar.gz` (`Slipdock.Skills`).
- `lib/slipdock_web/api_guide.ex` — the guide, generated per caller.
- `lib/slipdock_web/controllers/install_controller.ex` — `/install.sh`.
- `lib/slipdock_web/base_url.ex` — how the app works out which address to hand
  out, and why `conn.scheme` is not it.
- `cli/` — the escript. The Docker image builds it into
  `priv/cli/slipdock.escript`, and
  `lib/slipdock_web/controllers/cli_install_controller.ex` serves it with its
  checksum and the Windows installer (`priv/cli/install.ps1`) under `/cli/`.
- `lib/slipdock/runners.ex`, `lib/slipdock/runners/setup.ex` — the job queue
  and the Connect-a-runner generator; `priv/runner/` — the shell and
  PowerShell runners and their installers, served under `/runner/`.
