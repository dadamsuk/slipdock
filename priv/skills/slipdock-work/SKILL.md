# Working from the slipdock

The board is the plan of record: what to do next, and where the record of what
happened goes. **The server documents its own conventions — read them first,
once per session, before choosing or updating anything:**

```sh
slipdock guide                    # markdown, from GET /api/guide
```

Without the CLI on this machine — which is the usual case, since the CLI needs Elixir:

```sh
B="${SLIPDOCK_URL:-$(cat ~/.config/slipdock/url 2>/dev/null)}"   # ask the user if neither is set
curl -s -H "Authorization: Bearer $SLIPDOCK_TOKEN" "$B/api/guide"
```

The server's address comes from `$SLIPDOCK_URL`, else `~/.config/slipdock/url` (written by
`slipdock url` or by the server's `/install.sh`). If you have neither, **ask the user for the
address of their Slipdock** rather than guessing at one — a hosted board is something like
`https://app.slipdock.us`, a self-hosted one whatever name they reach it by.

Pass the token if there is one (`$SLIPDOCK_TOKEN`, else `~/.config/slipdock/token`).
The guide needs no token, but with one it ends with the user's actual boards,
every list on them, and which list is the ready list, the backlog, the one for
work in progress and the one for done work — which is exactly what you need in
order to pick something up.

**The guide wins over this file.** It comes from the running server, so it is
current: the endpoints, the vocabularies and the board layout in it are
generated at request time. This file only tells you to go and get it, and what
to do while you have not.

## Finding something nobody can name

`slipdock cards <board> --search Q` filters one board by substring. Its other filters ask about
state instead of words, and they are the ones that answer "what should I pick up": `--deps
ready` leaves out anything waiting on an unfinished card, `--no-assignee` leaves out other
people's work, `--due overdue` is what has slipped. So the eligible list is one call:

```sh
slipdock cards <board> --column "To Do" --open --deps ready --no-assignee
```

`slipdock search <words...>` is different: it matches by **meaning**, across every board the
user can see, and covers comments and status updates as well as cards. Use it when the user
describes a thing rather than naming it ("the card about the refund rounding problem"), when
what you want was probably said in a comment rather than a title, or when you do not know
which board to look on. Read the matched chunk it prints, then `slipdock card <id>` for the
whole card before touching it.

## The short version it will expand on

- **Epics and subcards.** A top-level card is an epic: an outcome, holding the
  priority, dates and discussion. The work lives in its subcards, one sitting
  each. Checklist items are the steps inside a task. New work you discover goes
  under the epic it serves, as a subcard — not as a new top-level card.
- **Picking.** Finish what is already in progress; then the ready list (*To
  Do*), and the backlog only when nothing there is eligible. Highest priority
  first, position in the list breaking ties. Skip anything completed, archived,
  blocked, waiting, or assigned to someone else — `--open --deps ready
  --no-assignee` does most of that skipping for you. When the card you land on has
  subcards, descend into it and work those to done before coming back up for the
  next top-level card.
- **Updating as you go.** Move the card to in progress and assign it to yourself
  when you start; comment at every decision, surprise or dead end; flag it
  (`blocked`, `waiting`, `review`) with a comment saying what you are waiting
  for; on finishing, set `completed: true` **and** move it to the done list.
  Complete an epic only when its rollup shows every subcard done.
- **Long-running work gets interim updates.** If the task will take more than a
  short sitting, comment at each milestone while it is still running — what has
  landed, what is left, anything that changed the plan — and move
  `percent_complete` with it. One write-up at the end is too late to be useful:
  a card in progress with nothing newer than the move on it reads as abandoned.
  An epic running across several sittings gets the same treatment, one line as
  each subcard closes.
- **Commit, and link it.** When the project is a git repository, commit the
  card's work once it is complete — before closing the card — with the card id
  (`#42`) in the commit message. The closing comment links to the commit, or to
  the PR if one was opened (`Commit: https://github.com/…/commit/abc1234`). With
  no remote to link to, give the short hash and branch instead.
- **Token cost in the write-up.** The closing comment on a card ends with a
  line giving the tokens the work used, e.g. `Token cost: ~135k tokens
  (context budget 15.00M → 14.86M, claim to close)`. Take a reading of the
  remaining-token counter (`total_tokens left` in system messages) when you
  claim the card and again when you close it, and give the difference. If
  several cards were worked in one stretch, measure each from its own claim.
  If no counter is visible, say "Token cost: not measured" rather than
  estimating. Add the same figure to the epic's progress comment.
- **Read their favourites first.** `slipdock favourites` lists the boards, lists,
  cards and saved views this person has marked — where they actually work,
  which a list of boards does not tell you. When "what should I work on next?"
  is asked without naming a board, a favourite is the strongest hint you have.
  They are personal: never add or remove one unless asked.
- **Archived boards are work that has been set aside.** `slipdock boards` leaves
  them out on purpose; `--all` shows them with an `archived` state. Everything
  on one still reads and writes, but never pick work off an archived board
  without asking, and never put new work there.
- **Write down what the card cannot hold.** A board says what is being done; it
  is a bad home for how something works, what was decided and why, or the shape
  of a thing. Those go on the board's **wiki** — `slipdock page ls <board>`,
  `slipdock page read <page>`, `slipdock page new <board> <title...>`. The test is
  whether it will be read again after this card closes: a decision, a runbook, a
  spec or an investigation's findings will be, and belongs on a page (linked
  from the card's closing comment by its code, `W-31`); progress, blockers and
  what happened *now* belong in a comment on the card. Never both — a page that
  repeats the comments is a page nobody trusts.
  Search before writing one (`slipdock page ls <board> --q <the thing>`): extending
  the page that exists beats a fourth page about deployment. Pass `--message` on
  every edit, and `--base-hash` on any edit to a page you did not just write
  yourself, so a save can never quietly land on top of someone else's.
- **Don't** delete cards (archive instead), rewrite a title to match what you
  actually did, tidy other people's cards, or leave a card in progress with no
  comment newer than the move. Archiving or reordering a whole **board** is
  further still from your business: only on an explicit ask, naming that board.

## When this applies

- "What should I work on next?", "carry on with the plan", "work through the
  backlog", "next task" → fetch the guide, then pick by its rules and say which
  card you took and why.
- "Put this plan on the board", "break this into tasks" → epics with subcards,
  per the guide's shape.
- You are already mid-task on something that came off the board → the card is
  where progress, decisions and blockers get written, as they happen rather than
  in one dump at the end.
- You finished something that came off the board → close it out on the board
  before reporting it done here.
- The work produced an answer someone will want again — a decision, a runbook, a
  gotcha, the shape of a design → a wiki page on that board, named in the
  card's closing comment.

One board is not work: **Getting Started**, the tour the server builds for a
new account. Its cards are instructions for a person to follow in the UI, so
never pick one up, finish one, or tidy the board. If it is the only board
there, say so and ask what the user wants doing.

For command and endpoint syntax, `slipdock --help` and the `slipdock` skill; the API
is the contract and the CLI is a convenience. Report card ids back to the user
as `#42` so they can find them in the UI, and call a board by its **code** —
the short, unique handle each board has (`qvm-v1-rem` for "QVM V1
Remediation"), which `slipdock boards` lists and every `<board>` argument
accepts. It is stabler than a name and unambiguous where a name is not.

## If the board is unreachable

`could not reach …` means the server is down or `SLIPDOCK_URL` is wrong, and `401`
means the token is missing or dead (the user makes one under **Account → API
tokens**). Say so and ask. Never guess at what is on the board, and never report
work as tracked when the write did not land.
